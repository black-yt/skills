# 后端定位与活动对话保护

## Windows/WSL 执行器错配

- Windows 侧 `CreateProcess` 报找不到 `/bin/bash`，同时工作目录是 `/mnt/...`，优先怀疑 Windows 执行器误拿 Linux shell/path。
- `codex-linux-sandbox` 不存在也可能是安装、包装器或版本问题；不能从单个字符串断言整个 WSL 损坏。
- 从实际执行器运行 `pwd`、检查 shell 与操作系统，再在授权工作目录里做唯一临时文件的“创建→读取→删除→确认不存在”闭环。
- 工具声称文件已写入但实际 shell 不可见时，先暂停业务文件编辑，定位执行器与文件视图，不反复换工具写同一项目。
- WSL agent 可执行 Windows 工具，Windows agent 也可按产品能力访问 WSL 项目；不要把项目路径当作强制更换 agent 的唯一理由。关键是执行器能正确解释 shell 与路径。
- 修复后保留用户原本需要的原生/WSL 模式。内置终端设置与 agent 环境是两项配置，不能互相替代。

## “卡住”不等于需要杀进程

1. 检查是否在等待审批、用户输入、网络响应、长工具调用或终端输入。
2. 在正确执行环境运行无副作用的 `pwd` 或 `git status`，确认 cwd 和当前分支。
3. 只重开卡住的终端面板，或用新会话做最小复现；先保留旧会话。
4. 若需要重启 App，等待活动任务结束或遵循用户明确给出的中断范围；任务要求不中断时，不能自行重启其宿主。

## 确认需要保护的状态

- 分别识别 Windows 原生、WSL CLI、App agent 和 SSH 远端的实际 home/`CODEX_HOME`。不要假定其中两个指向同一目录，更不要为登录修复切换或共享 Codex home。
- 根据当前版本确认文件布局。常见受保护内容包括 `sessions/`、`archived_sessions/`、`history.jsonl`、session index、`state_*.sqlite`、`thread_history_*.sqlite`、WAL/SHM、`config.toml`、`auth.json` 或 OS 凭据存储。
- 命名不是稳定 API；按实际目录和官方说明判断，不创建缺失的历史数据库来“修复”。
- `auth.json` 等价于敏感凭据；只验证存在性和元数据，不打印、不加入诊断压缩包、不推送仓库。
- 会话数量和文件名也属于用户状态。维护基线保存在私有位置，只在报告中输出必要计数和验证结论。

## 进程和文件的维护基线

- Linux 使用 PID 加 `/proc/[PID]/stat` 的 starttime，避免 PID 重用造成误判。解析 stat 时先处理括号中的 comm，不能简单按整个字符串的空格固定索引。
- 识别父子关系以及运行中的 app-server/proxy；不要打印完整命令行，命令参数可能含凭据。
- 记录原有会话文件清单和核心文件的设备/inode。修复后检查没有原文件丢失或替换；活跃文件增长允许存在。
- 验证原有进程 starttime 未变、状态非 zombie，并结合任务实际状态判断；单凭 PID 存在不能证明对话仍能工作。
- SQLite 正在写入时，普通复制主文件不能保证一致备份；需要 SQLite 在线备份或应用支持的快照。不要删除 `-wal`、`-shm`，也不要在网络排障中执行 VACUUM 或重建索引。

## 清理和恢复边界

- 大目录不一定是垃圾。历史、模型、工作树与 provider 配置不因占空间就自动可删。
- 不用 `rm -rf ~/.codex`、卸载清数据或注销全部账号处理代理故障。
- 只有已确认是可再生且无活动依赖的缓存，才在用户授权的清理范围内删除；无法判定的内容保留并说明。
- 修复登录不顺带同步历史、迁移数据库、切换 provider 或统一多个 Codex home；这些是不同任务。
- 任何有风险的操作前都先完成可独立的只读调查与可回滚修复，明确剩余影响；已有授权足够时直接继续，不增加重复审批。
