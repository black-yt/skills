# 方案选择与容量预算

## 选择桌面承载方式

| 需求或条件 | 优先方案 | 需要明确的边界 |
| --- | --- | --- |
| Linux Qt/VTK 科学软件、截图和键鼠、CPU rjob | Ubuntu 容器 + Xvfb + Openbox + llvmpipe | 成熟二进制组件；共享内核；CPU 承担 3D 渲染 |
| 独立内核、Windows、必须完整 VM | 具备 `/dev/kvm` 的外部 VM/KVM 宿主机 | 不在缺少 KVM 的开发机上强行嵌套虚拟化 |
| 多用户交互桌面、浏览器观看 | 在上述栈之上评估 VNC/noVNC 或成熟桌面服务 | 不是截图/PyAutoGUI 的必要依赖；额外端口、认证和存储另计 |
| 在已有 Mac 上运行 Slicer 原生版 | macOS 原生应用 | 不能作为普通 Linux 容器部署到 CPU rjob |

- **无需物理 GPU 的范围：** 2D GUI、截图和基础 VTK 场景可使用软件渲染；截图本身不需要 GPU。
- **不是完整 XFCE 的必要场景：** 单个应用只需 Xvfb 和窗口管理器。Openbox 提供窗口焦点、最大化和窗口交互，减少软件与故障面。
- **分辨率：** Slicer 官方最低要求 1366×768；样例用 1440×900×24。不要沿用早期 1280×720 探针而声称满足 Slicer 要求。
- **OpenGL：** `LIBGL_ALWAYS_SOFTWARE=1`、`GALLIUM_DRIVER=llvmpipe`、`QT_OPENGL=software`、`QT_QPA_PLATFORM=xcb`；实测 OpenGL 4.5 满足该 Slicer 版本要求。仅设置 Qt software 不能代替 VTK 渲染器核对。
- **线程：** 以 CPU 配额约束 llvmpipe、OpenMP 和 FFmpeg，避免按宿主机可见的所有核数启动线程。样例限制 llvmpipe 为 2 个线程。

## 分层估算存储

| 存储项 | 本次量级或建议 | 生命周期 |
| --- | --- | --- |
| Slicer 5.12.4 官方压缩包 | 498,717,156 字节，约 476 MiB | 项目软件缓存一份 |
| 固定 Python 源码归档 | 不到 1 MiB；Pillow/Tk 来自 apt | 项目软件缓存一份 |
| Slicer 解压目录 | 约 1.6 GiB；压缩包解压 tar 流约 1.61 GiB | 每会话临时目录，退出删除 |
| 分段下载与合并 | 临时同时存在分段和合并包，峰值约两份归档大小 | 成功校验后删除分段，失败保留以续传 |
| 基础镜像、apt 库和系统 Python | 取决于镜像和镜像缓存；不包括在以上数字中 | 容器层/集群镜像缓存，单独统计 |
| 截图、日志、视频 | 按动作保留截图；视频默认关闭，开启后有体积上限 | 用户项目的运行证据目录 |

- **多会话：** 共享归档不等于共享解压目录。并发 N 个会话要计入 N 份解压、进程内存和视频；不要通过只读软件缓存估算全部占用。
- **下载防膨胀：** 如果服务忽略 Range，每个并发请求可能下载整个包。脚本为每段配置 `max-filesize`，最终再用总大小和 SHA512 拒绝错误拼接。
- **缓存纪律：** HOME、XDG cache/config/runtime 放在独立临时会话目录；不让 Slicer、pip 和用户数据写入共享默认 home。Python 安装使用项目选择的独立 target。
- **保留策略：** 会话默认最多 1 小时；录屏默认关闭，开启后 5 FPS、H.264、约 256 MiB 文件限制。FFmpeg 的 `-fs` 是近似上限，可能因编码封装略超；它也不限制跨 run 总量。需要长期运行时另设轮转/总配额。
- **恢复边界：** 临时 HOME 和应用目录退出即清理；需要持久化的影像、场景和配置应显式保存到项目数据目录，不能把自动清理当作持久化。

## 资源证据的解释

- **已测：** 2 CPU / 8000 MiB / 0 GPU，Slicer GUI、2210 顶点球面、输入、拖动和录屏；容器 cgroup 内存峰值约 2.58 GiB，含文件缓存。
- **建议起点：** 同类基础桌面先用 2 CPU / 8 GiB；更重场景可从 4 CPU / 16 GiB 开始重新测量。
- **未测：** 大型 CT/MRI、体渲染、分割计算、长时间稳定性、多会话吞吐；不能把球面实验的内存或视频体积外推到这些负载。
- **优化顺序：** 先缩小输入数据和记录频率、控制线程及缓存；有证据表明软件渲染达不到目标后，再评估 GPU/DRI。不要为基础 GUI 预先引入 GPU 编译或设备直通。
