# 长时间监督与异常接管

## 建立任务所有权

- 顶层为每个中层指定唯一 owner、管线集合、可写候选目录、只读输入、禁止项、验收命令和交付期限。多个中层不得同时恢复同一会话或写同一共享状态。
- 中层可诊断、准备补丁、运行小型聚焦检查；live 接线、共享配置、provider/session 身份、资源预算、发布和任务启停由顶层或现有 owner 按具体授权执行。
- 文件系统只读隔离有助于保护 live 目录，但不能代替网络、作业提交、API 权限控制。候选目录应与真实管线产物分开。

## 变化触发的陪跑循环

1. 用确定性代码采集小快照：独立事项数、真实完成凭据、stage、owner/lock、队列、最新失败原因与最近活动时间。限制扫描范围、文件数量和单文件大小。
2. 无变化时只做便宜轮询；阶段变化、失败、长时间无活动或到达复核周期时才调用中层模型。提示只附快照路径、近期变化、必要日志尾部与已知约束。
3. 对每条管线保留 session ID、监督进程 PID 与启动标识、CLI PID、独立锁、最近心跳、状态、日志和 STOP 文件。一个监督循环同一时刻最多运行一个 Claude 子进程，不递归开新 agent。
4. 模型调用设置墙钟超时及有限退避。超时只终止该监督器创建的进程组；不能误杀底层 worker。重启前确认旧 owner 与 CLI 已退出、锁可取得，再续接原 session；不得盲目重复提交 job。
5. 停止时写 STOP，由监督循环收尾自己的调用并退出。恢复前核对实际进程、启动标识、锁及最新状态；旧报告不证明监督仍在运行。

合理的起点是约 60 秒的确定性轮询、状态变化时调用模型、无变化时较低频复核；具体周期按故障响应要求和服务延迟调整。Atria 回应慢时应减少重叠调用，不能把墙钟耗时直接当 CPU 占用。

## 资源回压与扩容

- 先从一个外部中层启动，在任务独立且机器有余量后再增至两个。更大并发需实际负载数据、服务延迟和互不冲突的 owner 支持；“100 项分 10 组”只说明分批结构，不保证同开 10 个会话。
- 以容器/作业实际 CPU 配额、可用内存、load、当前 agent 和重型进程为准。参考门槛：1 分钟 load 达可用 CPU 的 70%，或可用内存低于 `max(4 GiB, 总内存 25%)` 时停止新增调用。
- 可用 `nice` 降低优先级；长期硬限额用 cgroup 或作业系统。开发机只做轻量监控、少量源码读取、精准编辑与小检查；大规模扫描、数据复制、构建和训练交给有资源隔离的执行环境。
- 记录每次调用的开始、结束、退出码、超时与退避。服务慢或故障时不通过提高并发、无限重试或全局重启掩盖问题。

## 异常转成可执行交付

中层报告至少包含：

- 当前真实状态、与上次相比的变化、证据路径和未确认的推断。
- 异常的 owner、最小复现、原因边界、候选补丁与实际运行的聚焦检查。
- 需要顶层批准或执行的具体动作、受影响对象、风险与回滚前提。
- 完成门禁尚缺的原生执行、校验、发布或实体检查。

同一原因连续误判/失败两次、约 15 分钟仍无可执行复现或候选、反复权限试探、扩大修改范围、与另一 owner 冲突时，顶层接管。中层继续照看未受影响任务，并交接具体阻塞，不能只循环写“仍在运行”。

顶层审阅实际 diff、作用范围、真实来源绑定和反例；候选补丁与 passing test 不能代替底层完整运行的原生验收。不要代造完成标记、科学验证、发布结果或资源清理证据，也不要通过改变历史失败预算或抢占 worker 来制造成功状态。
